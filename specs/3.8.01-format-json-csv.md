# 3.8.01 — Format de sortie (ex-« Format JSON/CSV »)

Répond au point **3.8**, outil 1, point par point.

Rappel : « Modèle » (T1), « Ce qu'il fait » → Description (T2), « Rôles ET Effet » (spec 1.1,
Tableau de bord) et « Clé d'API » (T4) sont déjà traités transversalement, pour les dix outils —
pas répétés ici.

## Fait central, trouvé dans le code

Il existe déjà **8 formats de sortie** déclarés dans `pilote/formats/` : CSV, JSON,
FollowTheMoney, GeoJSON, GEXF (réseau), texte, webhook, xlsx — chacun un petit fichier qui se
déclare lui-même (nom, description, quels « contenus » il sait produire). Le mécanisme est déjà
pensé pour grandir seul : **« ajouter un format = ajouter un fichier »** (commentaire du code), y
compris des formats « perso » posés dans un dossier de configuration, découverts automatiquement,
sans toucher au cœur du programme. C'est exactement ce que demandait le pavé (« menu déroulant
fermé, mais géré dynamiquement si un format est ajouté ») — déjà construit, juste pas branché sur
cette tuile, qui se limite aujourd'hui en dur à CSV et JSON.

**Décision** : la tuile se renomme **« Format de sortie »** (elle ne se limite plus à JSON/CSV) et
lit ce registre.

## 1. Format de sortie : menu fermé, dynamique

Le menu n'affiche plus deux cases en dur mais la liste réelle de `pilote.formats.vue()` : CSV,
JSON, FollowTheMoney, GeoJSON, GEXF, texte, webhook, xlsx, plus tout format « perso » ajouté par
momo. On peut en choisir plusieurs (déjà possible aujourd'hui pour CSV+JSON, étendu aux huit).

## 2. Une section dédiée à chaque format choisi

Chaque format déclare déjà ce qu'il sait produire (`contenus`) — pas besoin d'inventer un système :

* S'il n'a qu'un seul contenu possible (FollowTheMoney, GeoJSON, GEXF) : rien à régler, pas de
  section.
* S'il en a plusieurs (CSV : nom / nom+ville+pays / détail complet ; JSON, texte, webhook, xlsx :
  nom / détail complet) : un choix fermé supplémentaire apparaît, propre à ce format.
* CSV, et lui seul, affiche en plus le **Séparateur** (`;` ou `,`, déjà tranché) — parce que c'est
  le seul format où un séparateur a un sens.
* Un format qui déclare un besoin externe (ex. webhook a besoin d'une URL) affiche le champ
  correspondant, lui aussi déjà déclaré par le format (`besoin`) — pas un champ à ajouter à la
  main pour chaque nouveau format, juste à lire la déclaration.

C'est la « section dédiée à chaque format » demandée : elle se construit depuis ce que le format
déclare de lui-même, donc elle suit automatiquement tout nouveau format ajouté, sans nouveau code
d'interface à chaque fois — c'est ce qui la rend robuste.

## 3. « Ajouter un format, avec test de compatibilité »

Pour qu'un format ajouté ne casse rien (« c'est la clé de voûte du programme »), on reprend le
principe déjà utilisé pour les outils eux-mêmes : chaque outil a un `test_entree`/`test_sortie`
d'exemple, vérifié par les tests automatiques. Un format ajouté par momo doit avoir le même : un
petit exemple d'entrée/sortie vérifié par un test automatique avant toute mise en service — pas un
testeur en direct dans l'interface, un filet de sécurité dans le code, cohérent avec le reste de
grappes.

## 4. Ce qu'il reçoit / Ce qu'il renvoie

Vérifié dans le code : « Ce qu'il reçoit » n'est jamais un choix pour cette tuile — c'est toujours
« les résultats de la recherche ». Seul « Ce qu'il renvoie » varie, et il n'a pas besoin d'un menu
séparé : il se déduit automatiquement du ou des formats choisis en 1 (ex. « Un fichier CSV » ou
« Un fichier CSV et un fichier JSON » si les deux sont choisis).

## Ce que momo change

* `suite_plan.py`, genre `format` : valide contre `pilote.formats.vue()` au lieu de la liste figée
  `("csv", "json")`.
* `reglages.js` / `ui.js`, fiche de la tuile : menu « Format de sortie » rempli depuis l'API (une
  route qui expose `pilote.formats.vue()` existe déjà probablement pour l'export — sinon en
  ajouter une, en lecture seule) ; section de contenu + séparateur + champs `besoin` générés
  dynamiquement par format choisi, pas codés en dur un par un.
* `suite_graine.py`, `_OUTILS` : renommer `"Format JSON / CSV"` → `"Format de sortie"`, mettre à
  jour `fait` (description) en conséquence.
* Documentation `suite/pilote/*.md` : même renommage là où la tuile est citée.
* Un test automatique minimal par format (point 3) — à ajouter pour les formats qui n'en ont pas
  encore, pas seulement les nouveaux.

## Comment momo vérifie

* Créer une tuile Format, vérifier que les 8 formats apparaissent dans le menu, pas seulement
  CSV/JSON.
* Choisir CSV : la section « contenu » (nom/nom+ville+pays/détail) et le séparateur apparaissent.
  Choisir GeoJSON : aucune section, rien à régler.
* Choisir webhook : le champ URL apparaît (venant de sa déclaration `besoin`), absent pour les
  autres formats.
* Ajouter un format « perso » de test dans le dossier prévu : il apparaît dans le menu sans
  redémarrage de code, seulement un rechargement de la page.
* « Ce qu'il renvoie » affiche bien les formats choisis, sans qu'on ait à les ressaisir ailleurs.
