# 3.8.03 — Condition « si »

Répond au point **3.8**, outil 3. Rappel transverse déjà traité ailleurs : Modèle (T1), Ce qu'il
fait → Description (T2), Rôle/Effet (spec 1.1), Clé d'API (T4, pas pertinente ici — aucun service
externe).

## Fait trouvé en répondant à une question de Sednal : le tri n'est pas branché

« si » ne fait jamais que **trier** — garder ou éliminer des résultats selon le test, sans jamais
modifier un résultat gardé. Mais en vérifiant jusqu'au bout : la fonction qui fait vraiment ce tri
(`suite_plan.appliquer()`) existe, est testée, mais **n'est appelée nulle part dans le programme
qui tourne** — seulement dans les tests (`test_suite_plan.py`). Aujourd'hui, poser une tuile
Condition ou Filtre dans un plan ne change donc rien à un résultat réel : seul le message de
validation à l'écran dit que « ça s'applique ». **Ce document ajoute son branchement réel au
périmètre de momo**, sans quoi tout le reste de cette spec resterait cosmétique.

## Ce qui ne marche aujourd'hui qu'avec UNE seule condition

`_etape_champ()` (`suite_plan.py`) ne sait tester qu'une chose à la fois : un champ, « est égal à »
une liste de valeurs. C'est le « trop restrictif » du pavé. Demande explicite de Sednal,
inspirée du nœud IF de n8n (en plus simple) : plusieurs conditions, et plus de comparateurs —
mais seulement ce qui est réellement utile sur les champs de grappes, qui sont tous du texte
simple (pas de nombre/date/booléen comme dans n8n).

## 1. Plusieurs lignes de condition, combinées par ET/OU

La tuile accepte désormais plusieurs lignes (champ + comparateur + valeur), plus un choix global
pour toute la tuile — pas de groupes imbriqués, juste un combinateur simple :

* **Toutes les conditions (ET)** : chaque ligne doit être vraie.
* **Au moins une condition (OU)** : une seule ligne vraie suffit.

Exemple : « Catégorie est égal à Association » ET « Ville est égal à Lyon » → seuls les résultats
Association ET à Lyon vont dans « oui ».

## 2. Comparateurs : 8 choix fermés, tous utiles sur du texte

| Comparateur | Exemple |
| :-- | :-- |
| est égal à | Catégorie est égal à Association |
| est différent de | Pays est différent de France |
| contient | Nom contient Foot |
| ne contient pas | Nom ne contient pas Junior |
| commence par | Nom commence par FC |
| finit par | Nom finit par Club |
| est vide | Site est vide *(aucun site trouvé)* |
| n'est pas vide | Numéro officiel n'est pas vide |

« est vide »/« n'est pas vide » ne demandent pas de valeur (le champ valeur se cache). Les autres
acceptent une liste séparée par virgules (OR entre les valeurs d'une même ligne, comme aujourd'hui
pour « est égal à »).

Pas de « contient une expression régulière » (trop technique pour les champs visés, risque de
casse) ni de comparateurs numériques/date (les champs de grappes n'en ont pas).

## 3. Champ : menu fermé réel

`CHAMPS` (déjà fermé côté moteur : nom, ville, pays, genre/catégorie/type, origine, site, numéro,
fonction) devient un vrai menu déroulant dans l'interface au lieu d'un texte libre vérifié après
coup.

## 4. Ce qu'il reçoit / Ce qu'il renvoie

Clarifié, pas un menu : « Reçoit : une liste de résultats » / « Renvoie : deux listes — oui (ce qui
remplit la ou les conditions, selon ET/OU) et non (le reste) ».

## Ce que momo change

* `suite_plan.py` : `_etape_champ()` devient `_etapes_conditions()` — accepte une liste de lignes
  `{champ, comparateur, valeurs}`, un mode `et`/`ou`, et les 8 comparateurs ci-dessus au lieu du
  seul « égal à ». Le résultat d'une branche est `garder`/`ecarter` selon le mode choisi appliqué à
  toutes les lignes.
* `reglages.js`, fiche Condition : « Champ » en select fermé ; une ligne par condition avec un
  bouton « + Ajouter une condition » (sur le modèle de « + Ajouter une source/un outil » déjà
  existant dans l'app) ; un choix ET/OU en haut ; comparateur en select fermé, 8 valeurs, qui
  cache le champ valeur pour « est vide »/« n'est pas vide ».
* Même mécanique réutilisée pour **Filtre** (3.8.06) qui partage `_etape_champ()` aujourd'hui —
  cohérent, un seul moteur de condition pour les deux tuiles.
* `charte/nommage.md` : ajouter les 8 comparateurs et ET/OU comme mots fermés si besoin.
* **Branchement réel** : `taches.py`, `ContexteRecherche.ajouter_candidats()` appelle
  `suite_plan.appliquer(lignes, self.parametres.get("plan") or {}, lancer_script=None)` avant
  d'écrire les `Candidat` — seules les lignes gardées sont enregistrées. Le `bilan` renvoyé (combien
  de noms chaque tuile a retirés) part dans le journal via `self.noter(...)`, sur le même principe
  que le compteur par tuile déjà prévu en spec 1.1. Sans plan (recherche simple), rien ne change :
  `appliquer()` avec un plan vide garde tout.

## Comment momo vérifie

* Une condition seule, « est vide » sur Site : les résultats sans site vont en « oui ».
* Deux conditions en ET : seuls les résultats qui remplissent les deux vont en « oui ».
* Les deux mêmes conditions en OU : plus de résultats en « oui » qu'en ET.
* « commence par » / « finit par » sur Nom : comportement attendu, pas de casse sur un nom vide ou
  avec caractères spéciaux.
* **Le plus important** : lancer une vraie recherche (pas juste valider le plan) avec une tuile
  Condition posée — vérifier dans les `Candidat` enregistrés que les résultats écartés n'y sont
  vraiment pas. Avant ce document, ils y étaient quand même.
