# 3.6 — Changer la clé (ou les clés) d'une source

Répond au point **3.6** du pavé de Sednal du 02/11/2026 : « On doit pouvoir modifier/changer la clé
API ou tout autre élément extérieur permettant de faire fonctionner une source. »

## Ce qui existe déjà

* **La clé simple** se change déjà dans le panneau (`ficheSource`, `reglages.js`) : un champ mot de
  passe, jamais réaffiché une fois enregistrée.
* **Les paramètres non secrets** (ex. l'adresse d'un portail CKAN) se changent déjà aussi — réglé le
  02/11/2026, même jour que ce pavé (`definir_parametres`, `suite_reel.py`).

## Le vrai trou

Une source peut demander **plusieurs** valeurs secrètes — Reddit, aujourd'hui seule dans ce cas,
déclare :

````yaml
cle:
- REDDIT_CLIENT_ID
- REDDIT_CLIENT_SECRET
````

Le moteur le sait (`Declaration.cles: list[str]`, `sources.py` ligne 54). Mais tout le chemin
d'écriture ne garde que la **première** :

* `sources.py` ligne 130 : `cle = liste_cles[0] if liste_cles else ""` — la liste est réduite à un
  seul nom dès le chargement.
* `suite_reel.ecrire_cle()` écrit sous ce seul nom.
* Le panneau n'affiche qu'**un** champ mot de passe.

Résultat : pour Reddit, on ne peut enregistrer que `REDDIT_CLIENT_ID` depuis l'interface —
`REDDIT_CLIENT_SECRET` n'est atteignable par aucun bouton. C'est précisément le « tout autre élément
extérieur » que Sednal signale.

## Ce que momo change

### Le moteur

`Declaration` garde déjà la liste complète (`cles`) — ne pas la perdre à l'étape `sources.py:130`.
Exposer la liste entière, pas le premier élément seul, dans ce que l'API renvoie pour une source
(`cles_noms` existe déjà en interne, ligne 74 — le vérifier déjà présent dans la réponse de
`GET /api/sources` et `GET /api/reglages`).

### La route

`PUT /sources/{ident}/cle` prend aujourd'hui `{ "valeur": "…" }`. La faire accepter une valeur par
nom de variable :

````json
{ "valeurs": { "REDDIT_CLIENT_ID": "…", "REDDIT_CLIENT_SECRET": "…" } }
````

Pour une source à une seule clé (77 sur 78), l'appelant envoie toujours un seul couple — **aucun
changement côté panneau pour ces 77**. `suite.enregistrer_cle` boucle sur les couples reçus et
appelle `cles.ecrire(cfg, nom, valeur)` pour chacun ; ignore une clé vide (on peut en remplir une
seule des deux sans effacer l'autre).

### Le panneau

`ficheSource` affiche aujourd'hui un seul champ `cle`. Le remplacer par **un champ par nom de
variable** de `s.cles_noms` :

````js
const champsCle = (s.cles_noms || [s.cle]).filter(Boolean).map((nomVar) =>
  champ({ libelle: nomVar, type: "password", autocomplete: "new-password",
    aide: "Elle ne s'affiche plus une fois enregistrée." }));
````

Le libellé est le **nom de variable lui-même** (`REDDIT_CLIENT_ID`), pas un mot inventé : c'est ce
nom que Sednal doit retrouver dans la documentation du fournisseur pour savoir quoi coller où, et
`nommage.md` ne définit pas de mot générique pour « identifiant d'application » vs « secret
d'application » — deux sources futures à deux clés pourraient avoir des noms très différents
(`CLIENT_ID`/`CLIENT_SECRET`, `APP_KEY`/`APP_SECRET`, `USER`/`TOKEN`…). Inventer un mot générique
masquerait cette différence plutôt que de l'expliquer.

Pour une source à une seule clé, `s.cles_noms` vaut `[nom]` : un seul champ, identique à aujourd'hui
visuellement, sauf que le libellé devient le nom de variable plutôt que « Clé d'API » générique —
amélioration cohérente avec le même principe.

## Comment momo vérifie

* Une source à une clé (ex. Tavily) : toujours un seul champ, s'enregistre comme avant.
* Reddit : **deux** champs, chacun s'enregistre indépendamment ; remplir un seul des deux ne touche
  pas à l'autre.
* `GET /api/sources` (ou `/api/reglages`) renvoie bien la liste complète des noms de variables pour
  Reddit, pas seulement le premier.
* Un test qui déclare une source à deux clés en fixture, remplit les deux depuis l'API, et vérifie
  que `cles.presente()` est vrai pour les deux noms de variable.
